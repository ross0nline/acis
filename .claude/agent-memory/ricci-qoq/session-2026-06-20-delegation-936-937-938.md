## Key Facts Learned

- **QueueItem has 27 fields** (not 28 as some docs claimed; the "28" came from counting
  DB columns including computed/joined ones). Interface properties: id → moment_id.
  The parity comment in types/index.ts now says 27 explicitly.

- **sweep_count: two different things**
  - `queue_items.sweep_count`: explicit opt-in review counter. PATCH body `sweep: true` only.
    Currently always 0 on all items because callers rarely pass sweep:true.
  - `dna_files.sweep_count`: auto touch counter, server-side increment on every /dna/file call.
    Mirrors frontmatter sweep_count in .md files.
  - A rename of queue_items.sweep_count → review_count touches 5 locations (new migration,
    types/index.ts, items.ts line 243, system-state.md, conventions.md). dna_files untouched.

- **REST/MCP write path parity is solid.** Both use identical 19-column INSERT SQL.
  Key divergences are param-name mapping (MCP: notes→description, session_id from metadata)
  and event logging (REST logs item_updated; MCP logs stage_changed only). The refactor
  (createItemCore/patchItemCore helpers) would require a translation layer for the param
  differences — moving the divergence, not eliminating it. Current side-by-side layout
  is more auditable.

- **system-state.md sweep_count bumped to 9** by linter after our edits (auto-increment hook).
  Conventions.md bumped to 7. Architecture-gap-analysis.md bumped to 5. These are accurate.

## Open Questions

- Is `queue_items.sweep_count` intended to ever be non-zero? Currently always 0. If the
  sweep: true PATCH flag is never used by any client, the column is effectively dead.
  Worth a live query: `SELECT COUNT(*) FROM queue_items WHERE sweep_count > 0`.

- The MCP `patch_item` omits the `sweep: true` mechanism. If sweep:true is ever used,
  MCP won't expose it. Minor but worth noting if review_count rename happens.
